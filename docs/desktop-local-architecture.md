# PAPOT desktop local architecture

Status: accepted V1 desktop architecture, refreshed after the September 13, 2026 audit. This technical note does not replace the official PAPOT AGENCEMENT cahier des charges.

## User-facing model

PAPOT is installed on each Windows workstation and launched from a normal application icon.

On the first launch only, the workstation setup collects and verifies:

- the shared company data/document path, for example `\\SERVEUR\\PAPOT`;
- the PostgreSQL connection used by the local PAPOT application server;
- the Nextcloud HTTPS address;
- the dedicated Nextcloud technical login;
- the Nextcloud application password;
- a human-readable workstation name such as `PC Lucien` or `PC Nadia`.

The setup does **not** bind a PAPOT business user to the workstation. PAPOT users authenticate with their normal account and the active session provides the user identity for rights, history and shared-resource locks.

After validation, workstation setup is persisted locally and is not requested on each launch.

## Secrets

The Nextcloud application password and PostgreSQL credentials must never be written in plaintext to the normal PAPOT configuration file, committed to Git, written to the cahier des charges, or sent to logs.

The desktop wrapper stores local secrets using Windows-backed encrypted storage. The normal workstation configuration contains only non-secret connection metadata and logical secret references.

## Stable workstation and user identity

Each installation owns a stable `device_id` UUID.

Shared-resource locks and important actions identify:

- the authenticated PAPOT `user_id` from the current server session;
- the workstation `device_id` generated at installation;
- the current user display name only as presentation metadata.

No random local `papot_user_id` is generated by workstation setup.

Reinstalling PAPOT is treated as a new workstation enrollment unless an explicit recovery flow is implemented later.

## Business data authority

PostgreSQL is the V1 source of truth for PAPOT business data.

The desktop installation may keep SQLite/local-only state for configuration, cache, device state and pending synchronization work, but shared business truth must not silently diverge into an independent per-PC copy.

PostgreSQL is not planned for removal from the V1 architecture. It remains behind the local PAPOT application layer and must never be exposed directly to the Internet.

## Shared resources and documents

Nextcloud remains the shared synchronization/document authority for files, document transport, shared-resource versions and leases/locks where those mechanisms are required.

The validated edit flow is:

1. read the latest resource version;
2. atomically acquire its Nextcloud lock;
3. if another active lock exists, open read-only and show its holder;
4. renew the lease while editing;
5. before save, verify the lease and expected resource version;
6. conditionally save the next version;
7. release the lease on normal close/save;
8. expired leases can be taken over safely after their TTL.

The real Nextcloud probes have already validated lock acquisition, renewal, read-only contention, release, handover and stale-version rejection.

## Shared company path

The configured Windows path is used for company documents and other files that belong on the shared storage. It must be an absolute Windows drive path or UNC path. Relative paths are rejected during setup.

Availability of that path is tested during setup/startup. Loss of access must not silently redirect writes to another folder.

## Desktop wrapper

Target wrapper: Electron for the Windows desktop implementation.

Electron and the NSIS installer are already integrated and have been packaged successfully. The wrapper reuses the Next.js/React application and Node-side logic, provides Windows filesystem access, uses `safeStorage` for local secret encryption, and exposes PAPOT as a normal installed Windows application.

## Network behavior

No inbound Internet port is required on PAPOT workstations and PostgreSQL is never published to the Internet.

PAPOT initiates outbound HTTPS to Nextcloud and, where required by mobile synchronization, to the minimal HTTPS relay retained by the V1 architecture. The relay is a transport boundary only and must not expose PostgreSQL or a general PAPOT backend to the public Internet.

Closing PAPOT may delay workstation-side processing until an authorized PAPOT worker/workstation is available again. This is accepted for the current V1 architecture.

## Audit corrections to implement

The September 13 audit confirmed the architecture and identified the following implementation corrections:

1. first-launch setup must configure and verify the PostgreSQL connection, not rely only on an external `DATABASE_URL` already present on the machine;
2. workstation setup must stop asking for a PAPOT user and must never generate a local random PAPOT user id;
3. locks, history and sensitive actions must use the authenticated PAPOT user plus the stable `device_id`;
4. desktop/API modules must enforce rights server-side, with the UI only reflecting those rights;
5. obsolete documentation describing a future removal of PostgreSQL or forbidding the validated minimal HTTPS relay is superseded by this note and by the official cahier des charges.

## Next implementation sequence

1. apply the PostgreSQL first-launch configuration and encrypted secret handling;
2. remove workstation-bound PAPOT user identity and use authenticated sessions everywhere;
3. finish server-side permission enforcement and the Admin user/right screens;
4. merge the duplicate Capture/Entrées paths around PostgreSQL as the single business source of truth;
5. continue module-by-module audit and cleanup before building the native Devis/Facturation flow.
